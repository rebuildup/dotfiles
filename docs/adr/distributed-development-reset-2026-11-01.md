# 分散開発基盤の旧方式を不採用とする決定と失敗記録

- 日付: 2026-11-01
- 状態: ユーザー指示による旧方式の採用中止。新方式は要件のみ確定、未実装・未検証。
- 対象: 2026-10-24以降の分散ノードPoC、登録同期、専用worker/controller、共有表示hostを積み重ねた方式。
- 判断: この一週間の成果を完成への前提として引き継がない。旧方式を修理し続ける作業を中止する。

## 何が起きたか

ユーザーは、Mac・Windows・WSLのどこからでも必要な実行先を選び、同じHerdrセッションの同じtabを開けば同じターミナル内容が見えることを求めていた。各端末のローカル作業も引き続き使える必要がある。選択tabの自動追従は不要と明示されている。

しかし最新のユーザー観測では、WindowsにWSLが2件、Macに1件表示され、その3件がすべて違うものを開く。WindowsローカルのHerdrも使えず、Macの共有だけになっている。これは未完成というだけでなく、登録対象と日常の起動経路を統一できていない状態である。3件の正確なOSインスタンス/server/session対応は未照合であり、同一WSLの重複だと断定して削除してはならない。

過去のSSH nonce一致、API成功、reachable、特定tabの一時的な入出力一致は、その時点・対象の限定的な証拠として残す。現在の通常起動で同じ作業ができる証拠にはならない。旧文書の「現在使える」「接続を維持」等は現状保証として撤回する。

## 何がいけなかったか

| 失敗 | 具体的な実装・進め方 | ユーザーへの結果 | 本来すべきこと |
| --- | --- | --- | --- |
| 接続先の正本がない | Gitの表示名、端末別private binding、SSH alias、Herdr profile、named/default sessionを別々に調停した | 同じWSL名でも別の対象が開く。端末ごとに件数が違う | Infisicalの同一ノード定義から接続対象を解決する |
| 共有対象を取り違えた | 表示名同期や疎通確認を進捗の中心にし、試験用セッションを増やした | onlineでも普段の作業は一致せず、長いPoC workspaceが並ぶ | 実際に使うserver/session/tabを指定して両画面を照合する |
| 操作元と実行先を混同した | Macへのremote接続や共有表示hostを解決策として広げた | Windows自身の作業を開けない状態を残した | Windowsローカルと他ノードへの接続を共存させる |
| 最小の利用体験より基盤を先行させた | Headscale同居、OS分離worker、gateway、controller、修復journal、MI、maintenanceを並行して追加した | 利用不能のまま運用経路と障害箇所が増えた | 既存の到達可能な経路で同一ターミナル共有を先に完成させる |
| 実行権限・起動方法を整合させなかった | Windows elevated serverと通常clientの不整合、Linux非sudo workerへ既存pc-setupの利用を期待した | Windowsのlocal接続失敗、workerのsudo失敗 | 日常の通常起動とOSセットアップの実行主体を先に確認する |
| 部分検証を利用可能性へ拡張した | 専用tab/API/ログ上の成功と、ユーザーが開く実画面の成功を混同した | 成功報告の後もReconnectingや別内容が続いた | 通常入口での両方向操作・再接続まで確認し、未確認を明示する |
| 修復をユーザーに反復させた | 固定hash付きcontroller v1〜v4等の手動実行を重ね、実行形態の違いも吸収できなかった | 一週間かけても再利用できず、操作負担が増えた | 根本の対象・責務を見直し、同じ失敗への修復追加を止める |

OS分離や最小権限自体を誤りとするものではない。ユーザーが承認したそれらの要件を、画面共有を完成させる前に大きな独自基盤へ展開し、通常の利用と両立させなかったことが誤りである。設計承認を得た事実は、要件未達を正当化しない。実装と検証の責任はエージェント側にある。

## 本当に必要な最小構成

```text
Infisical: 許可されたノードの接続先の正本
    ↓ 明示的な取得・登録同期
Mac / Windows / WSL のHerdr client
    ↓ 既存の認証済み通信経路 + Herdr公式接続
対象ノードの実作業Herdr server / session / terminal
```

Infisicalは接続先と必要な認証情報を管理する。画面やPTY、workspaceを複製する場所ではない。Herdrが同一server/sessionのターミナルを共有する。接続先を保存するだけでネットワーク到達性やSSH認可が生まれるわけではないが、そのために別の中央スケジューラーや共有表示サーバーは必要ない。

1. ノードごとに、論理ID・instance ID・表示名・OS/実行環境・接続先host/port/user・確認済みhost key・接続対象Herdr session・アクセス対象を一つの定義として管理する。新たなschemaやInfisical保存pathはこの記録では発明しない。
2. 各clientは許可された同じ定義を読み、Herdr公式機能で同じ対象へ接続する。ローカルprofile IDや端末内の鍵pathは一致する必要がない。対応先が一致することが必要。
3. private key、ログインcache、agent認証を全端末へ配布しない。接続先情報へのアクセスと対象ノードへの認可は別に維持する。
4. 各ノードは実作業用のHerdr sessionを提供する。検証のために別sessionを増やして普段のsessionの代替にしない。ローカルで開く作業とremoteで開く作業を一致させる。
5. 登録同期は同じ入力で重複を増やさない。更新・削除は自分が管理する登録だけを対象にする。未登録の既存WSLを勝手に採用・削除しない。
6. Macの導入経路はmise。OSインストール・SSH/service設定はpc-setup、接続情報取得と薄いuser wrapperはdotfiles。Herdrの機能は再実装しない。

初期の必要操作は接続先の取得/同期・一覧・接続と、その実測確認だけ。新たなVPN制御層、独自join/leave state machine、中央オーケストレーター、VPSの共有Herdr、専用worker生成をこの共有機能の前提にしない。再生成・失効・厳密なworker隔離という元の要求は消去せず、共有機能の成立後に独立した必要性と範囲を検討する。

## 受入条件を具体的に固定する

- 全端末で許可されたノード集合が一致し、同一ノードを指す重複登録がない。Local表示の差や端末固有profile IDの差は許容する。
- 各登録について、実行OS/user/instance、Herdr server/sessionを照合できる。表示名の一致だけでは合格にしない。
- MacとWindowsから同じWindows tabを開き、両側の入力・出力が相互に表示される。Windowsの通常ローカル起動でも同じ作業に戻れる。
- MacとWindowsから同じWSL tabを開き、同様に一致する。実在する複数WSLを登録する場合はそれぞれ区別し、試験用の別sessionを台数に数えない。
- 2つ目のtabを作ると双方から同じtabと内容を選べる。片側clientを切断して再接続しても同じ作業に戻る。
- Mac clientを閉じてもWindows自身とWSLの作業は継続できる。Mac上の実行processがMac停止で止まることとは区別する。
- 同期の再実行で登録が増えず、接続不能時に別ノード・別sessionへ暗黙fallbackしない。
- 以上を通常の起動入口で実測するまで「使える」「完成」と報告しない。APIだけの試験は補助証拠に限定する。

## 何を破棄し、何を残すか

今回の「破棄」は旧方式を製品・運用の採用候補から外し、追加開発と復旧の連鎖を止めること。稼働中データを無差別に消す意味ではない。

| 対象 | 決定 | 現時点の実施状態 |
| --- | --- | --- |
| 旧ADR、実装計画、表示名だけの同期手順 | 不採用・歴史資料化。今後のセットアップ手順に使わない | 冒頭に撤回表示を追加 |
| dotfiles PR75、pc-setup PR143/147を含む旧方式の候補 | そのまま採用・mergeしない。今後の方式の必須依存にしない | この記録で採用中止。PR close・branch削除・revertは未実施 |
| 独自devnode/controller/maintenance実装 | 継続開発の前提として破棄。必要なら独立要件から再評価 | 証拠保全のためソースは残存。稼働機への適用を追加しない |
| PoC Herdr登録、named session、共有VPS Herdr | 撤去候補 | 現在の参照・作業有無の照合前には削除しない |
| 専用Windows account/WSL、gateway、SSH/service/task、MI | 撤去/整理対象の棚卸しが必要 | 稼働状態・依存を未確認。削除・失効・停止は未実施 |
| ユーザーworkspace、既存Ubuntu、鍵、Codexログイン、Infisical既存project | 保存 | この記録作業では変更しない |
| 脆弱性対応済みバージョンと安全な設定 | 機械的rollbackの対象外 | 古い脆弱な版へ戻さない |
| 実測ログ・失敗記録 | 保存 | 新方式の成功証拠として再利用しない |

撤去は、対象の所有者・実際の接続先・残存作業・他ノードの依存を照合し、作業を保持してから、不要な登録→不要な常駐資源→専有認可の順で個別に行う。共有VPNや既存Infisicalを巻き込まない。実機撤去と新方式の実装はこの文書作成では実施していない。
