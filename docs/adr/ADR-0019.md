# ADR-0019: Router execution contract — classify once, keep the verdict, run the route you authorized

- Status: Accepted
- Date: 2026-11-18
- Layer: Current practice / agent routing, not Constitution
- Related: [#86](https://github.com/rebuildup/dotfiles/issues/86) (Epic), [#92](https://github.com/rebuildup/dotfiles/issues/92) (classified failure), [#100](https://github.com/rebuildup/dotfiles/issues/100) (Herdr dispatch), [#136](https://github.com/rebuildup/dotfiles/issues/136) (opt-in continuity), [#139](https://github.com/rebuildup/dotfiles/issues/139) (same-harness fallback)
- Extends: [ADR-0014](ADR-0014.md) (OMP Worker, strict default), [ADR-0015](ADR-0015.md) (route identity and attestation), [ADR-0017](ADR-0017.md) (bounded continuity), [ADR-0018](ADR-0018.md) (free-tier portfolio)

## Context

The router executes a task on one authorized route and, when a fallback profile
is configured, may continue it on a pre-authorized candidate of the same
harness. The pieces that decide *what ran* and *why it failed* were written
independently, and three defects let a run report something other than what
happened:

1. **The verdict was thrown away at the boundary.** The executor classified a
   failure correctly (`auth`, `billing`, `quota-exhausted`, …) but reduced it
   to a category name inside an exception message. The caller then rebuilt a
   blank signal and re-classified it, so every exhausted fallback reported
   `unknown` — the one category that means "we do not know", produced
   precisely when the cause was known.
2. **The primary route was never executed.** The executor iterated the
   profile's *candidates* only. The route the task was actually requested on
   was used for quota-scope comparison and nothing else, so a run could
   succeed on a provider the request never named.
3. **The worker was started without its credential.** A Herdr worker is a
   separate process owned by the Herdr server; it inherits the *server's*
   environment, not the dispatcher's. The worker started, accepted the prompt
   and then failed with `No API key found for <provider>` — reported as an
   auth failure that looked like a provider-side rejection.

A fourth defect made the first invisible: the launcher's own provider list
in the router was a hand-maintained array of provider keys. It was missing
routes that exist, and it passed the launcher route key where OMP needs the
provider's native `omp_id`. A route absent from that array started its worker
on OMP's default provider — a different account than the route authorized.

## Decision

### 1. One classification, carried structurally

A failure is classified once, from structured evidence, and the verdict
travels with the error. `FallbackExhaustedError` carries the last
`ClassifiedError` as `lastError`; the caller reads that instead of
re-deriving a category from a blank signal. A category of `unknown` is
produced only when there is genuinely no evidence, never as a substitute for
a verdict that was computed and dropped.

### 2. An unrecognized failure stops the chain

An `unknown` classification is not evidence that another candidate would
serve better. Per ADR-0017 §3, an unknown fact must not silently change
accounts, billing, or execute a new mutable attempt. The executor therefore
stops on `unknown` and reports it, instead of advancing.

### 3. The primary route runs first

The executor tries the profile's `primary_route` first, then the resolved
candidates in order. The candidates exist to *continue* the primary when it
is unusable; executing only the candidates would run a provider the request
never named.

### 4. A candidate runs on its own worker, with its own route, model and credential

Provider and model are pinned when a worker starts, so a candidate — a
different route and model on the same harness — needs a fresh worker rather
than the primary's. Each candidate gets its own pane and worker started with
that candidate's `omp_id`, model and credential, and the pane is closed
afterwards.

### 5. The provider id and the credential come from config, never from a list

The worker is started with the provider's `omp_id` (the id OMP knows, which
can differ from the launcher route key — `openrouter-free` is `openrouter`),
and the model roles are pinned for credentialed providers so a role switch
cannot reach another, possibly paid, model. The credential is read from the
dispatcher's environment (populated by `script/with-secrets`) and passed to
the pane through Herdr's `--env`; a credentialed provider whose credential is
absent fails before a worker starts, rather than burning a prompt on a
guaranteed auth failure.

### 6. The launcher is importable

`script/agent.ts` exports its config surface and runs its CLI only when it is
the process entry point. Router modules import the config types from it
instead of duplicating them, and a test can build a real `Config` without
executing the launcher.

### 7. A worker's answer is its terminal output, and it is returned as such

`herdr agent prompt` reports the agent's **state**, not its answer; the text
lives in the agent's terminal output, which is a screen dump containing the
prompt, the reply and the surrounding UI. The router therefore reads the
worker's output and returns it under an explicit `output` name. Nothing
parses a reply out of it: a screen dump has no reliable structure, and
guessing would be worse than returning what the terminal actually showed.

## Consequences

- A failure reports the category that was observed. `auth` stays `auth`
  instead of becoming `unknown`.
- An exhausted fallback names the reason, and a caller can distinguish a
  quota exhaustion from an auth failure without re-running anything.
- A task runs on the route it was requested on, unless that route is
  unusable, in which case it continues on an authorized candidate.
- A Herdr worker reaches the provider it was started for.
- A route added to the config needs no code change to be reachable from the
  router.
- The classification vocabulary has one owner (`limits.ts` is the taxonomy;
  the router reuses it) rather than a second copy that can drift.

## Verification

- `bun test script/agent.fallback-exec.test.ts` — the classified category
  survives exhaustion (`auth`, `network`, `billing`); an `unknown` failure
  stops after the first attempt instead of advancing; a classified
  non-transient failure advances through the primary and then the profile's
  candidates in order.
- `bun test script/agent.task.test.ts` — the worker options carry the
  provider's `omp_id` (not the launcher route key), include a provider that
  the old hand-maintained list omitted, pin the model roles for credentialed
  providers, and refuse an anonymous provider. A missing credential fails
  before a worker starts. The attempt outcome is recorded in the task state
  with its classified reason.
- `bun test script/agent.herdr.test.ts` and the router suite — `createPane`
  reads the pane id from the CLI's actual response envelope, which previously
  produced no id at all.
- Real providers, measured 2026-11-18 through the Herdr dispatch path with
  `script/with-secrets`: `omp.kilo` (Nemotron 3 Ultra, free) and `omp.groq`
  (GPT-OSS 120B, free) both answer a prompt through a Herdr-started worker.
  Before the credential fix the same worker reported `No API key found for
  kilo`; before the primary-first fix a fallback request ran on the candidate
  instead of the requested route.
- Real classification, measured: `omp.mistral` and `omp.openrouter` return
  HTTP 402, which the router classifies as `billing` (it previously surfaced
  as `unknown`).
- Not verified: Windows/WSL real calls, concurrent tasks on one profile,
  and the exact rate-limit boundary where a provider flips from usable to
  exhausted.
