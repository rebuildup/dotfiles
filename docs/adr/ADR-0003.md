# ADR-0003: SOPS + age as the portable secret bootstrap boundary

- Status: Accepted
- Date: 2026-09-23
- Classification: Project-local Operating Policy / Practice
- Extends: ADR-0001, ADR-0002
- Superseded by: None

## Context

The public dotfiles repository can reproduce configuration structure, but it cannot contain plaintext API keys, tokens, private keys, or other secret material.

Keeping those values as unrelated local files would make machine bootstrap depend on undocumented manual state. The desired model is to keep reproducibility while reducing the human-held bootstrap state to one root secret.

SOPS supports age recipients in `.sops.yaml`, keeps encrypted files suitable for version control, and can pass decrypted key/value data directly to a child process through `exec-env` without first materializing a plaintext environment file.

## Decision

1. SOPS + age is the canonical store for **portable secret material** used by this dotfiles environment.
2. The age private identity is the bootstrap root secret and MUST remain outside Git.
3. The corresponding age public recipient is public metadata and SHOULD be committed in `.sops.yaml`.
4. SOPS-encrypted payloads MAY be committed to this public repository.
5. API keys, tokens, and other environment-shaped secrets SHOULD be consumed with `sops exec-env` or the repository helper rather than decrypted into persistent plaintext files.
6. Secret files that genuinely need filesystem materialization require an explicit restore path with restrictive permissions. They are not linked through `home/`.
7. SSH keys are device identities by default. New devices SHOULD generate distinct SSH key pairs. A specific SSH private key may be treated as a portable SOPS-encrypted file secret only by an explicit decision.
8. SOPS and age installation belongs to `pc-setup`; this repository owns the configuration, encrypted payloads, and consumption/bootstrap contract.
9. `~/.config/sops/age/keys.txt` is the default local root-identity path for this repository's helpers. `SOPS_AGE_KEY_FILE` may override it.
10. A new machine bootstrap follows: install tools -> restore/generate age identity -> establish public recipient config -> validate decryption -> consume secrets.

## Security properties

- Plaintext portable secrets are not Git state.
- Possession of repository contents alone is insufficient to decrypt secrets.
- The root private identity is never created inside the repository tree.
- Environment secrets can be scoped to an explicitly launched process rather than every login shell.
- Device-specific SSH identity and portable secret backup are separate concepts.

## Consequences

The age private identity becomes high-value material. Losing it without another configured recipient can make encrypted secrets unrecoverable; compromise can expose every payload encrypted to that identity.

The identity therefore needs an external backup under the user's control. The backup mechanism is deliberately outside this repository.

Secret names/keys in structured SOPS files can remain visible even when their values are encrypted. Secret key names MUST therefore avoid carrying sensitive values.

## Rotation

When the age identity is replaced or compromised:

1. add the new public recipient to `.sops.yaml`
2. run `sops updatekeys` on encrypted files
3. remove the old recipient
4. update keys again and rotate SOPS data keys where appropriate
5. rotate the underlying API keys/tokens that may have been exposed

## Re-evaluation triggers

Reconsider this Practice if:

- a hardware-backed or cloud KMS becomes preferable as the primary root
- multiple operators require independent access/revocation
- one root identity creates unacceptable blast radius
- secret audit/access-control requirements exceed local age identity semantics
