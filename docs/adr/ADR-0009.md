# ADR-0009: Implement the agent launcher in Bun + TypeScript (no Python)

- Status: Accepted
- Date: 2026-10-17
- Classification: Architecture / Tooling
- Extends: ADR-0004, ADR-0006, ADR-0008
- Supersedes: None

## Context

The unified `agent` launcher (`agent <harness> <provider>` /
`<harness>-<provider>`, driven by `config/agents.toml`) was first
implemented as a single-file Python 3 script (`script/agent-launcher`,
`tomllib`, stdlib only). It worked, but it conflicted with the workspace
tooling policy: **new Python scripts are prohibited** (project-init
ADR-0001, policy-overview "新規Python scriptは禁止"). The launcher also has
to run on three platforms from one implementation — macOS and WSL today,
Windows native next — and each platform must use the same
`config/agents.toml` with the same Infisical secret handling.

The runtime constraint is narrow: parse TOML, build a filtered environment,
start a native CLI. `bun` is already a cross-platform machine baseline tool
(pc-setup `mise.toml`, `mise.global.toml`, WSL verify) and provides
`Bun.TOML.parse()` with zero added dependencies.

## Decision

1. **The launcher is `script/agent.ts`, executed by Bun.** One TypeScript
   implementation serves macOS, WSL/Linux and Windows; the long-term
   implementation language for dotfiles automation runners is Bun +
   TypeScript. Python stays only where it predates this ADR and is
   unrelated (e.g. pc-setup's kanata installer).
2. **No new dependencies.** TOML parsing uses `Bun.TOML.parse()`; stdlib
   (`node:fs`, `node:path`, `node:os`) covers the rest.
3. **No `execve` semantics.** Bun cannot replace the current process, so
   every launch spawns the native CLI as a single child with inherited
   stdio (interactive TUIs, exit codes, Ctrl+C forwarding verified on
   macOS; signal death maps to 128+signal).
4. **Same CLI, same config, same secrets.** All previously shipped CLI
   forms, exit codes (2 usage / 1 runtime), the two-stage
   `script/with-secrets` protocol, per-provider ENV filtering and model
   resolution are unchanged. Windows uses the PowerShell mirrors
   `script/agent.ps1` and `script/with-secrets.ps1` and starts the
   `infisical` CLI natively.
5. **Shortcuts stay name-derived from routes.** Unix provides symlinks to
   `script/agent.ts`; the invoked name is recovered from the kernel-level
   argv (`/proc/self/cmdline` on Linux, `ps -o args=` on macOS) because Bun
   resolves symlinked `argv[1]`. Windows generates minimal `.cmd` entry
   points that pass the route name explicitly. `agent <harness>-<provider>`
   is the portable spelling everywhere.

## Consequences

- The launcher and its mock tests carry a `.ts` shebang and run under
  `bun`; CI installs Bun via the pinned `oven-sh/setup-bun` action.
- Mock tests (`script/agent.test.ts`, `bun test`) spawn bash stubs and
  therefore require a POSIX shell; Windows behavior is verified manually
  and recorded in `docs/agent-launcher.md`.
- The previous Python artifacts (`script/agent-launcher`,
  `script/test-agent`) are removed from the deliverable; they were used as
  the porting reference only.
- Future dotfiles automation should default to Bun + TypeScript (or plain
  POSIX shell where a process substitution is not needed); new Python
  scripts remain prohibited.
