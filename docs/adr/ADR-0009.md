# ADR-0009: Assign one owner to each global Agent Skill placement

- Status: Accepted
- Date: 2026-10-17
- Related: ADR-0005

## Context

ADR-0005 makes `dotfiles` the composition root for global agent configuration and plans a future `agents/common` repository for portable Agent Skills. It does not say what happens when another tool also writes to the same global Skill directories.

Two other writers already exist:

- **Tools that ship their own Skills.** Orca installs its Skill stubs (`orca-cli`, `orchestration`, and others) with `--global`. Its updater reinstalls them pinned to the commit of the running Orca build, and its Skills page scans the Claude, Codex, and Agent Skills global directories. The stubs only work when they match the installed app version.
- **Projects.** Project-specific Skills live in each repository, committed as files with a `skills-lock.json` (rebuildup/project-init ADR-0029 and ADR-0030).

If `dotfiles` also managed those Skills, two writers would update the same files on different schedules and silently undo each other.

## Decision

Each Skill has exactly one owner, chosen by where it must stay in sync:

| Skill | Owner | Placement |
| --- | --- | --- |
| Skills that must match an installed app version (for example Orca's stubs) | that app's own updater | global, written by the app |
| Portable Skills shared across all agents and projects | `dotfiles` via `agents/common` | global, linked by `script/link` |
| Project-specific Skills | the project repository | project-local, committed with `skills-lock.json` |

Rules that follow from this:

- `script/link` and future `agents/common` tooling never overwrite, delete, or relink a Skill directory that another owner installed. A name collision is a failure to resolve, not something to replace.
- `agents/common` does not vendor app-owned stubs, even when they look portable.
- A project does not depend on a global Skill being present. If a project needs a Skill, it commits its own copy.

## Consequences

- Orca's updater can keep its stubs current without fighting `dotfiles`.
- Removing an app removes its Skills without affecting `dotfiles` or any project.
- When `agents/common` is created, its link step must detect foreign Skill directories and stop instead of replacing them.

## Re-evaluate

- If an app starts reading its Skills from a location `dotfiles` can own without breaking its updater.
- If the skills CLI gains a lockfile restore that verifies content, which would let `agents/common` pin third-party Skills reproducibly.
