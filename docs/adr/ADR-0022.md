# ADR-0022: Antigravity CLI (agy) management and read-only review profile

- Status: Accepted
- Date: 2026-11-23
- Layer: Current practice / tool management, not Constitution
- Related: [#218](https://github.com/rebuildup/dotfiles/issues/218), [#219](https://github.com/rebuildup/dotfiles/issues/219) (harness follow-up), rebuildup/pc-setup#230 / PR #231 (mise baseline)
- Research: [docs/research/antigravity-cli-2026-11-23.md](../research/antigravity-cli-2026-11-23.md)

## Context

The operator runs Google AI Pro and wants a read-only visual review harness on
macOS driven by the Antigravity CLI (`agy`, Google
`google-antigravity/antigravity-cli`, observed 1.5.14). Before this change the
binary was a standalone `~/.local/bin/agy` install outside any package manager,
and nothing in dotfiles described which parts of its state are managed versus
machine-local.

Two properties of `agy` shape the design:

- **Credential store follows the environment.** With `SSH_CONNECTION`,
  `SSH_CLIENT` or `SSH_TTY` present, `agy` selects file-based token storage at
  `~/.gemini/antigravity-cli/antigravity-oauth-token`; without them it uses the
  OS keyring (macOS Keychain). A desktop login therefore does not authenticate
  an SSH session, and an SSH login does not authenticate a desktop session
  (upstream: google-antigravity/antigravity-cli#1336, #1514).
- **Headless permissions are deny-by-default for prompts but not for allowed
  defaults.** In `agy -p` (print) mode a tool call that would prompt is
  auto-denied and reported in `denied_actions`, yet `command(*)` still
  executes by default policy. Read-only behaviour therefore requires explicit
  `permissions.deny` rules, not just the absence of `--dangerously-skip-permissions`.

## Decision

### 1. Binary ownership stays in pc-setup mise; dotfiles owns only the shim

`agy` is added to `rebuildup/pc-setup` `mise.global.toml` (`latest`, aqua
backend `google-antigravity/antigravity-cli`) alongside `claude`/`codex`.
dotfiles does not duplicate version management. `home/.local/bin/agy` (and the
`antigravity` sibling name via symlink) is a thin launcher that resolves the
mise binary and normalizes the SSH credential-store split; it contains no
version pins and no credentials.

### 2. SSH/keyring normalization rule

When any of `SSH_CONNECTION`/`SSH_CLIENT`/`SSH_TTY` is set **and**
`~/.gemini/antigravity-cli/antigravity-oauth-token` does not exist, the shim
removes those three variables for the child (keeping `SSH_AUTH_SOCK`) so `agy`
uses keyring auth. If the token file exists the environment passes through
unchanged, preserving SSH-native logins. This mirrors the proven approach in
the community `hermes-antigravity-subscription` plugin.

### 3. Managed vs machine-local state boundary

Managed by dotfiles (reproducible, shareable):

- `home/.local/bin/agy` + `home/.local/bin/antigravity` — launcher shim
- `home/.config/agy/review.settings.json` — read-only `--settings` payload,
  linked to `~/.config/agy/review.settings.json` on every machine

Machine-local, never committed (contains account state, machine paths or
session history):

- `~/.gemini/antigravity-cli/` — `settings.json` (`trustedWorkspaces` is
  machine-specific), OAuth token file, conversation DBs, history, logs
- `~/.gemini/antigravity/`, `~/.cache/antigravity`,
  `~/Library/Application Support/antigravity` — IDE-side state
- macOS Keychain items (`svce=gemini`, `acct=antigravity`)

`script/link` is non-destructive: adopting `~/.local/bin/agy` requires moving
the pre-mise standalone binary aside once; `~/.config/agy/` has no prior
state. No composer/generator is added — the managed set is two small static
files, below the threshold that justified `script/claude-settings.ts`.

### 4. Read-only enforcement is permission rules plus post-checks

The review profile is `~/.config/agy/review.settings.json`, passed per
invocation with `--settings` (session-only, never persisted by `agy`):

```json
{ "permissions": { "deny": [
  "write_file(*)", "command(*)", "read_url(*)",
  "execute_url(*)", "mcp(*)", "unsandboxed(*)" ] } }
```

Verified on 1.5.14: `read_file` still works inside the workspace, `write_file`
and `command` fail with explicit deny-rule errors, and no files are created.
`toolPermission: "strict"` was evaluated and rejected — it prompts before
every tool including reads *even when an allow rule matches*, which makes
headless reads unusable.

`--mode plan` and prompt-level instructions are **not** accepted as the
read-only guarantee. The harness (#219) must additionally treat
`denied_actions`, tool permission errors in the response, and any workspace
mutation as review failure — `status: "SUCCESS"` alone is not sufficient
evidence.

### 5. Subscription auth only; quota is observable

Review runs use the Google account sign-in (`oauth-personal`, Google AI Pro
subscription). `gemini-api-key`, `agent-platform` (Vertex/ADC) and any
pay-as-you-go route are out of scope and must not be configured. `agy -p
"/quota"` returns structured quota state (weekly + 5-hour windows per model
group, `remaining_fraction`, `reset_time`) usable by a future scheduler.

## Consequences

- `agy` resolves through mise on machines that applied pc-setup; the shim
  fails closed with a clear message where mise has no `agy`.
- SSH-invoked `agy` (including future herdr/Rex workers) authenticates via
  keyring as long as no SSH token file exists; a deliberate SSH login keeps
  working through the token file.
- The read-only guarantee depends on the deny payload staying in sync with
  `agy`'s permission action set (`read_file`, `write_file`, `command`,
  `read_url`, `execute_url`, `mcp`, `unsandboxed`); new sensitive actions
  upstream must be re-evaluated when bumping `agy`.
- Harness construction, herdr routing and quota scheduling are deferred to
  #219.
