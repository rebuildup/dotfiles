# ADR-0004: Infisical as the secret source of truth

- Status: Accepted
- Date: 2026-09-23
- Classification: Project-local Operating Policy / Practice
- Extends: ADR-0001, ADR-0002
- Supersedes: ADR-0003

## Context

This environment spans local development, WSL/NixOS, CI, cloud workloads, and AI-agent-driven workflows.

SOPS encrypts files well, but keeping encrypted secret payloads in Git still leaves secret lifecycle outside a centralized authorization system. It also requires a separate decryption root identity, creates historical ciphertext that remains decryptable by that identity, and provides no native RBAC, per-access audit trail, workload identity, or rotation lifecycle.

Infisical provides a centralized secret store with user and machine identities, project/environment/path scoping, audit logging, rotation capabilities, and runtime CLI injection.

## Decision

1. Infisical is the canonical source of truth for portable secrets.
2. Secret **values MUST NOT be Git state**, even encrypted Git state, unless a future explicit decision establishes a separate GitOps requirement.
3. Human developer workstations authenticate as users through the Infisical CLI.
4. Local repositories bind to an Infisical project using `.infisical.json` when appropriate. This file is non-secret metadata and MAY be committed.
5. Runtime environment secrets SHOULD be injected with `infisical run -- <command>` rather than exported globally or written to persistent plaintext `.env` files.
6. Automated workloads MUST use Infisical Machine Identities. Prefer platform-native/OIDC/JWT/cloud authentication that yields short-lived credentials over static Universal Auth client secrets whenever the runtime supports it.
7. `INFISICAL_TOKEN`, Universal Auth client secrets, user session credentials, and Infisical local credential/cache state MUST NOT be committed or symlink-managed by this repository.
8. Secret creation, update, deletion, versioning, access control, and audit history belong to Infisical rather than Git review/release history.
9. `pc-setup` owns installation of the Infisical CLI. `dotfiles` owns user-facing bootstrap, project binding checks, runtime wrappers, and repository leak guards.
10. SSH private keys remain device identities by default and are not automatically converted into centrally shared portable secrets.

## Human workstation flow

A fresh machine follows:

1. install `git`, `gh`, and `infisical` via `pc-setup`
2. clone/link dotfiles
3. authenticate GitHub
4. authenticate Infisical
5. bind the repository to the intended Infisical project with `infisical init` if no committed binding exists
6. validate access with `script/secrets-doctor`
7. run commands through `script/with-secrets`

No independent root decryption key needs to be restored to the workstation.

## Automation flow

CI and agents do not inherit a human CLI session.

They use a dedicated Machine Identity with least-privilege project/environment/path permissions. Where possible, the runtime proves its identity using a platform-issued credential such as OIDC, AWS IAM, GCP/Azure workload identity, or Kubernetes service-account identity and exchanges that for a short-lived Infisical token.

Long-lived `INFISICAL_TOKEN` values are not the default automation model.

## Local credential storage

Infisical CLI uses the platform keyring where available. On Linux, the CLI's keyring wrapper can fall back to its encrypted-file backend when the OS keyring write fails. The resulting local Infisical credential/cache state remains machine-local and MUST NOT be linked into `home/` or copied into Git.

## Consequences

- secret updates no longer require a Git commit or push
- encrypted secret payloads disappear from normal repository history going forward
- access and mutation history move to Infisical's audit/versioning model
- access can be revoked per human or machine identity without re-encrypting every repository payload
- runtime credentials can be narrowed by project/environment/path and automation identity
- secret availability now depends on Infisical availability and account/project access

## Migration from ADR-0003

Before removing the previous SOPS payload from the active branch, its required values must be imported into the chosen Infisical project.

After successful import and runtime verification:

1. remove `.sops.yaml` and tracked `*.sops.*` payloads
2. remove SOPS/age bootstrap helpers and package requirements
3. rotate migrated credentials where practical
4. keep ADR-0003 only as superseded decision history

The former age private identity is no longer an active bootstrap credential and should be retained only as long as historical recovery is intentionally required.

## Re-evaluation triggers

Reconsider this decision if:

- Infisical becomes unavailable or unsuitable for required platforms
- a project specifically requires encrypted GitOps manifests as an artifact
- organization policy mandates a different central secrets backend
- self-hosting requirements materially change the trust/availability model
