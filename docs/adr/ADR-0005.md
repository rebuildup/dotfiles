# ADR-0005: Compose agent configuration through sibling submodules

- Status: Accepted
- Date: 2026-09-23

## Context

Claude Code, Codex, and OpenCode each have independent global configuration repositories. They contain tool-specific formats and runtime behavior, but some assets can be shared safely across agents.

The setup must work from a fresh machine, including when the agent repositories are private. It must also preserve the boundary established by `pc-setup`: package installation belongs to `pc-setup`, while user-level configuration placement belongs to this repository.

## Decision

`dotfiles` is the composition root for global agent configuration.

Agent repositories are pinned sibling Git submodules:

```text
agents/
  common/      shared portable agent assets
  claude/      Claude Code-specific configuration
  codex/       Codex-specific configuration
  opencode/    OpenCode-specific configuration
```

The current active submodules are:

- `rebuildup/my-claude-setting`
- `rebuildup/my-codex-config`
- `rebuildup/my-opencode-setting`

The shared repository is added when it exists and contains only assets that are actually portable across agent products.

Nested submodules are not used. `dotfiles` pins every child repository directly so one parent commit identifies the full user configuration state.

## Bootstrap ordering

Private submodules are not required during the initial `dotfiles` clone.

The bootstrap order is:

1. clone `dotfiles` without requiring recursive submodules;
2. establish Git identity;
3. authenticate GitHub and install the `gh` HTTPS credential helper;
4. synchronize and initialize pinned submodules;
5. link validated user configuration;
6. validate Infisical access;
7. verify the resulting state.

This avoids requiring private-repository credentials before the bootstrap has a chance to establish them.

## Shared assets

The common repository may own:

- global tool-neutral instructions;
- Agent Skills using portable `SKILL.md` packages;
- references, assets, and scripts that are genuinely reusable across agents.

The same global instruction source is exposed through product-specific names:

- Claude Code: `~/.claude/CLAUDE.md`
- Codex: `~/.codex/AGENTS.md`
- OpenCode: `~/.config/opencode/AGENTS.md`

Shared skills should use an Agent Skills-compatible source and be linked into only the discovery locations required by each product.

## Tool-specific assets

The common repository must not absorb configuration merely because it expresses a similar intent.

These remain tool-specific:

- Claude Code `settings.json`, plugins, hooks, and permission syntax;
- Codex TOML, providers, model switching, rules, and agent role formats;
- OpenCode JSON, providers, permissions, plugins, and OpenCode-specific agent definitions.

Where two products express the same safety policy using incompatible configuration formats, the semantic policy may be documented centrally, but product-specific enforcement remains in the product repository unless a deterministic generator is introduced deliberately.

## Cross-platform rule

Do not activate a symlink on every OS until its source is portable on every target OS.

In particular, absolute Windows paths, machine-local credentials, session state, caches, and generated runtime state are not portable configuration.

Unix may use symbolic links directly. Windows-native setup requires an equivalent link adapter and must not silently replace the source-of-truth model with copied files.

## Updates

Submodule commits are pinned. Bootstrap initializes the recorded commits and does not float to the latest child `main`.

Updating an agent repository is an explicit parent change:

1. update and validate the child repository;
2. advance the corresponding gitlink in `dotfiles`;
3. run dotfiles verification;
4. review the parent change through the normal release flow.

## Consequences

- one dotfiles commit identifies the exact agent configuration set;
- private repositories remain private while the public composition repository contains only URLs and commit pins;
- shared instructions and skills can be maintained once;
- tool-specific configuration remains independently evolvable;
- a fresh machine can authenticate before fetching private configuration.
