# ADR-0001: Plain symlink home-mirror deployment

- Status: Accepted
- Date: 2026-09-23
- Classification: Project-local Practice
- Superseded by: None

## Context

This repository needs a reproducible way to keep CLI configuration in Git while applications continue to read their normal paths below `$HOME`.

Representative public dotfiles use several approaches: custom bootstrap scripts, filename conventions, dedicated managers such as `rcm`, and copy-based bootstrap flows. The initial repository does not need templating, secret injection, package installation, or a large platform matrix. Adding a dotfile manager now would make basic configuration depend on another tool before there is evidence that its additional abstraction is needed.

The deployment mechanism must remain safe when run repeatedly and must not destroy pre-existing user configuration.

## Decision

1. `home/` mirrors paths below `$HOME`.
2. Managed regular files are deployed as file-level symbolic links from `$HOME` back into this repository.
3. `script/link` is the canonical initial deployment command.
4. Linking is idempotent: an already-correct symlink is accepted without mutation.
5. Linking is non-destructive: a regular file, directory, or symlink to another source is reported as a conflict and is not replaced automatically.
6. All managed targets are preflighted before link creation. If any conflict exists, the operation aborts before creating new links.
7. `script/check` verifies that every tracked source currently points to the expected repository file.
8. The initial implementation uses Bash and ordinary filesystem tools available in Linux, macOS, and WSL. No dedicated dotfile manager is a prerequisite.
9. Software installation and OS configuration are outside this mechanism.

## Guarantees

- A tracked dotfile has one visible Git source and the live configuration resolves to that source.
- Re-running the linker does not duplicate or rewrite already-correct state.
- Existing unmanaged state cannot be silently replaced by the bootstrap path.
- A detected conflict does not leave a partially linked new configuration.
- The mechanism has no bootstrap dependency beyond Git, Bash, and standard filesystem utilities.

## Limits

- Native Windows symlink semantics are not automated by the initial Bash implementation.
- The initial design does not provide templates, encrypted secrets, host profiles, or generated files.
- Moving the repository changes absolute symlink sources; re-linking requires resolving the old links deliberately.

## Alternatives considered

### GNU Stow

Stow is a small and established symlink manager. It is useful when package-style grouping and directory-tree adoption become valuable, but it adds a prerequisite without currently reducing enough project complexity.

### rcm

`rcm` provides mature symlink management, tags, host-specific behavior, and multiple source directories. Those features are not required by the initial repository.

### chezmoi

chezmoi provides broad cross-platform, templating, secret, and machine-variation features. That capability is intentionally deferred until there is evidence that plain files plus local overrides are insufficient.

### Copy-based bootstrap

Copying files into `$HOME` weakens the direct relationship between the versioned file and the live configuration and requires a synchronization step after every edit. Symlinks better fit the intended edit-in-place workflow.

## Re-evaluation triggers

Reconsider the Practice when at least one of these becomes material:

- repeated platform/host conditionals appear in scripts
- secret/template generation is genuinely required
- symlink lifecycle code becomes larger than the configuration it supports
- native Windows becomes a first-class target with incompatible semantics
- an external manager demonstrably provides the same safety guarantees with lower maintenance cost
