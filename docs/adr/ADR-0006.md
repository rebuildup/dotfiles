# ADR-0006: Pin the self-hosted Infisical control plane

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0004

## Context

ADR-0004 selected Infisical as the canonical source of truth for portable secrets. The original workflow could use the managed Infisical service because the CLI defaulted to the vendor control plane.

The active secrets store has now moved to a self-hosted Infisical deployment. Relying on the CLI's default endpoint is no longer acceptable because an expired/missing local session or a fresh machine could silently direct authentication toward Infisical Cloud instead of the intended control plane.

Self-hosting changes the operational trust and availability boundary, but not the core secret-handling model from ADR-0004.

## Decision

The canonical Infisical instance for this repository is:

- Site URL: `https://secrets.rebuildup.dev`
- API URL: `https://secrets.rebuildup.dev/api`
- Dotfiles project ID: `d4c2fc09-a923-4a38-9cf4-b51769aadb76`

These values are non-secret metadata and are committed.

`config/infisical.sh` is the canonical instance configuration for shell wrappers. It exports `INFISICAL_API_URL` so `infisical run` and related CLI calls target the self-hosted API.

`.infisical.json` remains the canonical project binding and MUST match the project ID above.

Interactive authentication MUST target the self-hosted site explicitly:

```bash
infisical login --domain=https://secrets.rebuildup.dev
```

Runtime wrappers MUST NOT depend on the Infisical Cloud default endpoint.

## Bootstrap

A fresh clone already contains the project binding. Normal bootstrap therefore does not run `infisical init`.

The sequence is:

1. install the Infisical CLI through `pc-setup`
2. load `config/infisical.sh`
3. validate the tracked project binding
4. attempt authenticated runtime access against the self-hosted API
5. if needed, perform user login against `https://secrets.rebuildup.dev`
6. validate runtime injection again

A missing `.infisical.json` is treated as repository/configuration drift and should be restored from Git, not reconstructed interactively.

## Runtime

`script/with-secrets` loads the canonical API endpoint, validates the project binding, and launches:

```bash
infisical run --project-config-dir=~/.dotfiles -- command...
```

Secret environment/path selection is still not added at runtime. Project ownership remains the scope boundary defined by ADR-0004.

## Automation

Machine Identities and workload authentication must target the same self-hosted control plane.

Static tokens remain discouraged. Prefer short-lived OIDC/cloud-native authentication where supported.

The instance URL and project IDs may be stored in repository/CI configuration because they are identifiers, not credentials. Tokens, client secrets, sessions, cookies, and local Infisical credential/cache material remain secret.

## Availability and trust

Self-hosting means secret availability now depends on the operation of `secrets.rebuildup.dev`, including:

- TLS/DNS availability
- application availability
- database/storage availability and backups
- self-host upgrade/rollback discipline
- identity/authentication configuration

A failure of the self-hosted instance may prevent new processes from obtaining secrets. This is an accepted operational dependency.

## Migration

The old managed-service project binding is retired.

Old project ID:

```text
0555acc3-ed2d-49f2-a8ff-d510cefb9285
```

New self-hosted project ID:

```text
d4c2fc09-a923-4a38-9cf4-b51769aadb76
```

Existing Cloud CLI sessions may remain in local keyring state, but repository wrappers explicitly select the self-hosted API and therefore do not rely on them.

## Re-evaluation triggers

Reconsider this decision if:

- the self-hosted instance moves to another canonical domain
- the project is recreated and receives a new ID
- a different secrets backend replaces Infisical
- availability requirements require a different control-plane topology
