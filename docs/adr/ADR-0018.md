# ADR-0018: Free-tier provider portfolio — $0 routes, measured roles, no paid drift

- Status: Accepted
- Date: 2026-11-13
- Layer: Current practice / agent routing, not Constitution
- Related: [#86](https://github.com/rebuildup/dotfiles/issues/86) (Epic), [#76](https://github.com/rebuildup/dotfiles/issues/76) (fixed `openrouter-free` model), [#135](https://github.com/rebuildup/dotfiles/issues/135)/[#136](https://github.com/rebuildup/dotfiles/issues/136)/[#139](https://github.com/rebuildup/dotfiles/issues/139) (opt-in continuity), [#90](https://github.com/rebuildup/dotfiles/issues/90) (probes), [#91](https://github.com/rebuildup/dotfiles/issues/91) (quota), [#94](https://github.com/rebuildup/dotfiles/issues/94) (recommendation)
- Extends: [ADR-0012](ADR-0012.md) (fixed free model, no automatic selection), [ADR-0014](ADR-0014.md) (OMP Worker, strict default), [ADR-0015](ADR-0015.md) (route identity and attestation), [ADR-0017](ADR-0017.md) (bounded continuity)
- Refines, does not supersede: the "no implicit fallback" rule stays the default. This ADR adds *explicitly selectable* free routes; it does not make any of them a fallback target.

## Context

OpenCode Go and OpenCode Zen allowances are finite, and this repository's
existing routes stop when those allowances or an account balance run out
(measured restrictions are already recorded in `config/agents.toml`:
MiniMax M Plan weekly 100%, OpenRouter weekly budget, DeepSeek 402). Agent
development therefore needs a way to keep working at **$0 additional
monthly cost** — no pay-as-you-go, no new subscription.

Seven provider candidates were reviewed. Their keys were already present in
the self-hosted Infisical `dev` environment (`KILO_API_KEY`,
`MODELSCOPE_API_KEY`, `SILICONFLOW_API_KEY`, `GROQ_API_KEY`,
`REQUESTY_API_KEY`, `SENSENOVA_API_KEY`) and OVHcloud AI Endpoints needs no
key at all. A key existing is not evidence that a route is free: ModelScope
returned `401 Authentication failed` for every request shape tried,
SenseNova returned `401 Forbidden` on both documented hosts, and SiliconFlow
answered `402 your account balance is insufficient` (plus
`403 Model disabled` for a nominally free model). Those three are therefore
**blocked, not configured** — there is no route to reach them.

## Decision

### 1. Only a proven-$0 route may be added

A provider gets a route only when all of the following hold, and the
evidence is recorded in the `[catalog.*]` tables:

1. it answers a real completion **and** a real tool call in our own measured
   run (not a provider claim);
2. the provider's own machine-readable catalog reports a zero price for the
   model ids used, **or** the endpoint is a documented anonymous free tier;
3. the measured response reports zero cost where the provider exposes cost;
4. the provider rejects an unentitled request instead of silently billing it
   (401/402/403/429), so an exhausted or misconfigured route fails closed.

Anything that fails (1)–(4) is recorded as a blocked candidate in
`docs/research/free-provider-evaluation-2026-11-13.md` and gets **no route**.
A route that cannot be proven free must not be reachable at all — that is
stronger than "documented as free but reachable".

### 2. Free routes are explicit opt-in, never fallback targets

No launcher path may select a free route implicitly. `claude`/`opencode`/`omp`
without a provider stays native; a provider is always named. This preserves
ADR-0012's fixed-model rule and ADR-0014's strict default.
`openrouter-free` keeps its single fixed id: this ADR adds *other providers*,
not a runtime selector.

Recovery after a 429 / exhausted allowance uses ADR-0017's opt-in continuity
profile, never automatic switching. Three `$0` profiles are declared
(`free-go-to-kilo`, `free-kilo-quota`, `opencode-requesty-quota`), each with
`global_max_spend = 0` so the resolver's spend arithmetic cannot authorise
spend. Candidates are bound to the primary's harness: OMP has no native
`requesty` or `ovhcloud` provider, so an `omp` profile may only name
`omp.kilo` / `omp.groq`.

### 2a. The resolver, not the profile author, enforces the boundary

Reviewing the pre-existing resolver showed its billing and quota checks were
effectively no-ops: a `free` candidate pointing at a metered provider was
accepted, an uncatalogued provider's billing was ignored, `max_spend` was not
checked against the billing boundary, and the "shared quota scope" comparison
built a fake key (`<provider>:<credential>`) instead of using the catalog's
scope. Those are exactly the paths by which a free-labelled candidate could
consume paid capacity, so they were replaced with real checks:

| condition | rejection |
| --- | --- |
| primary allowance not catalogued (scope key `null`) | `primary-quota-unknown` |
| provider billing not in `[catalog.providers.*].billing` | `billing-unknown` |
| declared boundary ≠ catalogued billing (incl. `free` on a paying provider) | `billing-boundary-crossed` |
| any non-free candidate under a `global_max_spend = 0` profile | `billing-boundary-crossed` |
| provider-wide `[catalog.providers.<id>.restriction]` | `provider-restricted` |
| route-wide `[catalog.routes.<id>.restriction]` | `attestation-restricted` |
| candidate harness ≠ primary harness | `harness-mismatch` |
| credential source `unset`, or not Infisical on a `require_infisical` provider | `credential-mismatch` |
| `free` candidate with a positive `max_spend` | `spend-cap-invalid` |
| billable candidate with no `max_spend` under a declared budget | `spend-cap-invalid` |
| candidate/global cap exceeded | `spend-cap-exceeded` |
| candidate effective scope == primary scope | `quota-exhausted-scope` |
| candidate scope not catalogued | `quota-scope-unknown` |

Unknown billing is never treated as free, an unknown **primary** allowance
rejects every candidate (the independence check cannot run, so skipping it
would manufacture fresh capacity), and a missing candidate scope is never
treated as independent — all fail closed. `billingMatches` keeps `free`
strictly free; `plan` is the flexible prepaid case (a `plan` or `subscription`
provider), and `subscription` is strict.

`global_max_spend = 0` means **$0**, not "no candidate declared a cap". A
`metered`/`plan` candidate with an omitted or zero `max_spend` contributes 0 to
the running total, so a budget-only check let it slip under a zero budget.
Candidates whose billing can bill at all are therefore rejected outright on a
zero-budget profile. Under a **positive** budget a billable candidate must
declare an explicit cap, otherwise `totalSpend` counts it as 0 and any budget
admits it.

**What a positive `max_spend` does and does not guarantee.** Only
`global_max_spend = 0` is a hard stop, because it admits only candidates that
cannot bill at all. A positive cap (or a positive `global_max_spend`) is a
**pre-execution admission check, not an enforced billing ceiling**: the launcher
never observes the provider's actual spend, cannot attribute cost after a
candidate is handed to a harness, and cannot see a provider-side reprice or a
model that becomes paid mid-run. Do not read "the resolver accepted this
candidate" as "this run is capped at `max_spend`". The only guaranteed ceiling
remains an **account-side** hard stop (a spend limit that rejects requests, or
pay-as-you-go switched off) — the launcher cannot see or change those settings
and does not claim to. The same caveat applies to `openrouter-free` and every
provider whose price the launcher cannot verify.

A **present** spend cap must be valid. The generic optional-integer helper
mapped any malformed value to "absent", which for a cap means "uncapped", so
`max_spend = -1` (an operator writing "deny") would have authorised unlimited
spend. A dedicated parser rejects a present-but-invalid cap while keeping a
genuinely absent one absent, and the trap helper was deleted so it cannot
return.

`credential: "unset"` is the schema's own "not authorized (default)" and is
rejected unconditionally; previously it was admitted for any provider without
`require_infisical`.

Candidates are bound to the **primary's harness** and this is enforced in the
resolver (`harness-mismatch`), not left to profile authors: the executor drives
one harness, so a cross-harness candidate would be handed to the wrong process.
`executeWithFallback` does not perform cross-harness migration (ADR-0017 §4).

The candidate's allowance uses the **same route-first, provider-second
precedence** as `effectiveQuotaKey` (`effectiveRouteQuotaKey`). Comparing by
provider scope alone would misjudge a candidate route that declares its own
quota — accepting one that shares the primary's effective allowance, or
rejecting an independent one.

Provider-wide restriction is checked in the resolver rather than during
seeding, because seeding has no route→provider mapping. Route-wide restrictions
are checked there too, because seeding can only attach a per-model fact to
models named in that route's `e2e` list — a restricted route without e2e (the
real `omp.deepseek` 402) would otherwise have no seeded entry at all. A route
under a restricted provider is rejected even when it carries its own fresh e2e
evidence: a provider whose allowance is unusable cannot be unlocked by
route-level evidence.

Both callers (`agent fallback` and `executeWithFallback`) share one
`buildFallbackCatalog(config, catalogFacts)` and load the same validated
catalog, so the CLI preflight and the executor cannot disagree about which
candidates are safe. `executeWithFallback` fails closed if the catalog is
invalid rather than falling back to weaker config-only information.

`agent fallback` also seeds attestations from the committed
`[catalog.routes.*]` e2e / restriction records, then merges local probe state
**by severity, then by evidence timestamp**. A `restricted` entry wins over any
non-restricted entry regardless of recency, because committed catalog evidence
is day-precision (`2026-11-04T00:00:00Z`) and a same-day local block would
otherwise tie and lose to the committed `verified-live` record — resolving a
blocked route as usable. Otherwise a strictly newer `evidence.at` wins, and a
tie or unparsable timestamp keeps the committed entry. Seeding does not bypass
freshness: an old committed observation still fails `isUsable()`.

### 3. The credential boundary follows the billing boundary

- **Free-tier-with-a-key (Kilo, Requesty, Groq)** uses
  `require_infisical = true`. The free allowance belongs to *this* account,
  so an ambient `KILO_API_KEY`/`REQUESTY_API_KEY`/`GROQ_API_KEY` must never
  be used: it was measured to win the fast path and fail with
  `Your authentication token is invalid`, i.e. it silently pointed the route
  at a different account. With the flag the ambient value is stripped before
  the wrapper and a missing Infisical value fails closed.
- **Credential-free (OVHcloud anonymous)** declares the new
  `anonymous = true` provider attribute. It has no secret, no env name, and
  no Infisical stage runs at all (`require_cred` stays empty, so
  `needsInjection()` is false). Config validation rejects
  `anonymous` combined with `secret`/`env`/`require_infisical`, and rejects
  `anonymous` without `base_url`. The OpenCode custom-provider block sends
  `env: []`, so OpenCode resolves no key.
  Anonymous is only sound because the endpoint enforces a *presented*
  credential: a request with no `Authorization` header is served, while one
  carrying an invalid `Bearer sk-…` returns 403 (measured 2026-11-13). An
  injected or ambient key can therefore never be silently spent there.

### 4. Adapter-specific endpoint spelling is explicit

Kilo and Requesty serve both an OpenAI-compatible surface under `/v1` and an
Anthropic-compatible `/v1/messages`. Claude Code appends `/v1/messages`
itself, so its `ANTHROPIC_BASE_URL` must be the **bare origin**; OpenCode
needs `/v1`. With the wrong spelling Kilo answers
`400 This endpoint only accepts the paths /chat/completions, /responses and
/messages`. A provider may therefore declare `opencode_base_url` to re-spell
the endpoint for the OpenCode custom-provider block; it requires
`opencode_npm` and defaults to `base_url`. `agent check` now also requires
that a provider declaring `opencode_npm` is actually reachable from at least
one `opencode` route, so the block can never sit silently inert.

### 5. Capability gaps are expressed as absent routes, not failing routes

- **Groq has no `opencode` route.** Re-measured 2026-11-13: *every* free Groq
  chat model (`gpt-oss-120b`, `gpt-oss-20b`, `qwen3.8-27b`) reports
  `x-ratelimit-limit-tokens: 8000`, so this is not a model-choice problem.
  OpenCode's system prompt plus tool definitions alone request ~9.9–10.7k
  tokens, so *every* real OpenCode turn is rejected with `429 Request too
  large ... Limit 8000` regardless of the output budget (512/1024/2048/4096
  all rejected). OMP's smaller prompt stays under the budget and completes
  real tasks, so the route exists for `omp` only. This is recorded as a
  per-model `discouraged_reason`, deliberately **not** as a provider-wide
  restriction — Groq is usable, and a provider-level block would have removed
  the working `omp.groq` route.
- **OVHcloud has no `claude` and no `omp` route.** The endpoint is
  OpenAI-compatible only (`POST /v1/messages` → 404). The Anthropic adapter
  additionally *requires* an auth token, and with a credential-free endpoint
  Claude Code would fall back to its own claude.ai login and leave the route
  silently — the adapter rejects `anonymous` providers instead. OMP has no
  native `ovhcloud` provider, and adding one would mean a machine-local
  `models.yml` outside the reviewed catalog (see below).
- **No `omp.requesty` route.** OMP has no native `requesty` provider either.
  OMP *can* declare custom OpenAI-compatible providers in
  `~/.omp/agent/models.yml`, but that would create a second, machine-local
  catalog outside review, and the launcher's own OMP credential guard rejects
  such overrides. Both are already reachable from OpenCode, so no capacity is
  missing. If this is ever wanted, the correct change is a reviewed launcher
  feature that generates the block from `agents.toml` (as the OpenCode adapter
  already does).
- **ModelScope / SenseNova / SiliconFlow have no route at all.** Their
  Infisical keys remain stored and unused; no launcher path reads them. Root
  causes were identified on 2026-11-13 and are **account-eligibility issues,
  not launcher defects** — see
  [`docs/research/blocked-provider-investigation-2026-11-13.md`](../research/blocked-provider-investigation-2026-11-13.md):
  ModelScope's token is valid but the account is not bound to an Alibaba Cloud
  account (the `.ai` host states this explicitly while `.cn` masks it);
  SenseNova's key is not matched to either Token Plan workspace (both hosts
  reject a bogus key identically); SiliconFlow's key is valid only on the
  international host, where the free chat IDs answer 402/403 because the
  account is not verified/entitled. Each needs a one-time console action by
  the account owner; none can be fixed from the repository.

### 6. Roles come from measured tasks, not from catalog claims

Each candidate was measured on two real agent tasks through the actual
harnesses — a from-scratch implementation task (create code, create tests,
run them, write a result file) and a bug-fix task (read a failing suite,
diagnose, edit only the implementation file, re-verify) — with the test file
checked for tampering. Results are in
`docs/research/free-provider-evaluation-2026-11-13.md`; the resulting roles
are:

| Route | Default model | Role |
| --- | --- | --- |
| `claude.kilo`, `opencode.kilo`, `omp.kilo` | `nvidia/nemotron-3-ultra-550b-a55b:free` | First choice: fast (10–40 s) and correct on both tasks in all three harnesses |
| `opencode.kilo` (`kilo-auto/free`) | router over free models | Equivalent quality; server-side free routing, so the specific model may change |
| `opencode.kilo` (`cohere/north-mini-code:free`) | code specialist | Alternative when the Ultra id is limited |
| `opencode.kilo` (`reflection/beam-free`) | 1M context | Large-context fallback, ~4× slower (158 s) |
| `claude.requesty`, `opencode.requesty` | `nvidia/nemotron-3-ultra-550b-a55b` | Independent path once Kilo's allowance is exhausted |
| `opencode.ovhcloud` | `gpt-oss-120b` | Last resort: no credential at all, but 2 req/min; prefer `gpt-oss-120b` (Llama 3.3 70B timed out at 600 s on the bug-fix task) |
| `omp.groq` | `openai/gpt-oss-120b` | Slow (320 s) third path; token-budget bound |

`Meta-Llama-3_3-70B-Instruct` on OVHcloud completed the create-task but not
the bug-fix task; it stays selectable with `--model` and is documented as
the slower option.

### 7. Quota scopes match the real shared allowance

Kilo and Groq are `account` scopes (`kilo`, `groq`); Requesty is an
`account` scope (`requesty`) because its free limits apply per organization
across all free models combined; OVHcloud is a `machine` scope
(`ovhcloud-anonymous-ip`) because its anonymous budget is per IP. Declaring
the conservative new-organization Requesty budget (200/day, 20/min) avoids
assuming a purchase history that the launcher cannot see.

### 8. Data handling is part of the route's terms

Every Kilo free id reports `mayTrainOnYourPrompts = true`, and Kilo's own
Auto Free documentation warns that prompts may be logged by the upstream
provider. The NVIDIA-hosted free ids are trial-only under NVIDIA's API Trial
terms. These routes are therefore for code and non-sensitive work; the
catalog `terms` strings say so, and the routes must not be used for
credentials, customer data or private material.

## Consequences

- Agent development can continue at $0 across three independent free
  accounts (Kilo, Requesty, OVHcloud) plus Groq on OMP, without touching the
  existing Go/Zen/Logfare/OpenRouter/Mistral routes (all still present and
  unchanged).
- Reaching a paid path now requires an explicit, reviewed TOML edit or the
  separate opt-in continuity profile of ADR-0017. There is no code path from
  a free route to a paid one.
- The allowlist is not a price guarantee: if a provider starts charging for
  an id, the launcher will still send it. Mitigation is the same as
  `openrouter-free`'s: re-check the live catalog, and keep an account-side
  spend limit / pay-as-you-go-off setting as the hard stop. The launcher
  cannot see or change those account settings and does not claim to.
- Free tiers are rate-limited in ways that make them unusable for long
  unattended loops (Groq 8k TPM, OVHcloud 2 req/min, Requesty 200 req/day).
  They are a continuity bridge, not a production capacity substitute.
- Blocked providers (ModelScope/SenseNova/SiliconFlow) become available again
  only by re-measuring and adding routes with fresh evidence; their stored
  keys are not evidence. Each cause is now identified and documented in
  [`blocked-provider-investigation-2026-11-13`](../research/blocked-provider-investigation-2026-11-13.md);
  all three are account-eligibility actions for the account owner, not
  repository changes.
- **Attestation freshness is time-bounded.** The committed free-tier evidence
  is dated `2026-11-13` and the freshness window is 7 days, so every `$0`
  continuity profile stops resolving after about 2026-11-20 until the evidence
  is refreshed. This is deliberate (stale capacity claims must not silently
  look healthy) but it means the `$0` safety nets are not "set and forget":
  re-measure and update the `[catalog.*]` evidence, or accept that the profile
  reports no usable candidate. Re-verifying is a bounded, cheap operation
  (`agent fallback <id>` shows the reason).

## Verification

- `agent check` (config validation) on the new providers/routes, including
  the new `anonymous` invariants and the `opencode_npm`-reachability rule.
- `bun test script/agent.test.ts` — the mock suite, including new cases for
  the Kilo per-adapter endpoint spelling, `require_infisical` stripping on
  free routes with a stale ambient key, a missing-Infisical failure, the
  credential-free OVHcloud route (no wrapper, `env: []`, no claude/omp
  routes), and the new config-validation failures.
- `bun test script/agent.help.test.ts` — `agent routes` reports
  `cred_kind: anonymous` for the credential-free route and still agrees
  between human and JSON output.
- `bun test script/agent.fallback.test.ts` — 73 cases. The anti-paid-drift
  group covers a free-labelled paid candidate, a metered candidate on a free
  provider, uncatalogued billing, a positive cap on a free candidate,
  unprovable and shared quota scopes, separate free accounts staying
  independent, plus: an unknown **primary** allowance rejecting every
  candidate, a provider-wide restriction rejecting a route that still has
  fresh e2e evidence, a `configured` (declared, unverified) provider
  restriction blocking, and a candidate compared by its own route quota
  (accepting an override that differs from a colliding provider scope,
  rejecting one that resolves to the primary's allowance).
  Later rounds add: `harness-mismatch`, `credential: "unset"` rejection, a
  billable candidate with no cap under a positive budget, contract-legal
  `value: null` restrictions (merge and resolver must not throw), and
  `primary_route` validation. The seeding group covers the durable record, a
  newer local observation overriding it, an older one **not** overriding it, a
  same-day local restriction beating a day-precision committed record, a block
  never cleared by recency, a timestamp tie keeping the committed entry, and
  freshness still applying. A `buildFallbackCatalog` group asserts the
  wiring: provider billing/quota/restriction and route quota overrides
  actually survive the config → `CatalogLike` conversion (a dropped field
  silently disables a safety check), and `effectiveRouteQuotaKey` precedence.
- `bun test script/agent.test.ts` — includes a regression test that runs
  `agent fallback` against a populated `AGENT_STATE_DIR/catalog`, covering the
  `readdirSync` crash and the null-value restriction shape end to end.
- `agent fallback free-go-to-kilo` etc. resolve `USABLE` from the committed
  catalog. `omp.openrouter` is now reported `provider-restricted` (OpenRouter
  itself carries a committed restriction, checked before the attestation) and
  `omp.openrouter-free` `attestation-stale`, so `omp-mistral-quota` correctly
  has no usable candidate.
- Verified with the real `Catalog`: today's free providers
  (`kilo`/`requesty`/`groq`/`ovhcloud`) are not marked restricted, while
  `zen`/`minimax` are; injecting a provider-level restriction on `kilo`
  makes an otherwise-fresh `omp.kilo` candidate resolve as
  `provider-restricted`.
- `bash evals/agent-router/controls.sh` — includes the
  "silent paid model fallback blocked" negative control.
- Real E2E (measured, recorded per route in `[catalog.routes.*.e2e]`): all
  seven new routes were exercised through the real launcher on macOS with
  Claude Code 2.1.322, OpenCode 2.2.7 and OMP 18.18.9.
- Not verified: Windows/WSL real calls, long sessions, behaviour at the
  exact rate-limit boundary, and whether any id remains free over time.
