## Problem and objective

The existing `agent` launcher intentionally pins one harness/provider/model per invocation, filters credentials to that provider and forbids implicit switching. These safeguards prevent billing and credential mistakes. They also mean a quota-exhausted worker can stop despite other *already authorized* usable capacity. Manually starting a different harness/model often requires rereading the ticket and reconstituting the work state.

The objective is **continue the same authorized work without silent billing, duplicate side effects or loss of the harness's useful native abilities**. It is not universal model-ranking, a new coding harness, a generalized UI, or a new task source of truth.

## Decision

### 1. Preserve native capabilities and current ownership

Keep the existing native CLI/harnesses, Worktrunk, Herdr, GitHub/Linear and project-init boundaries. `config/agents.toml` remains the one canonical provider/model/route/credential-name catalog. Secret values stay with the current Infisical/native-auth owners. GitHub Issue/PR/Git and project-controlled Spec/ADR remain durable task truth; local cache/telemetry and sessions are not equivalent sources.

No default T3 Code adoption, new daemon/proxy/gateway, bespoke harness, cross-harness common tool subset or global knowledge database is authorized by this ADR. Those mechanisms require a separate value/ownership justification. A UI may observe a session without acquiring concurrent authority to restart, destroy or reassign it.

### 2. Add an opt-in continuity profile, never an unconditional fallback

The launcher retains the strict single-route behavior as its default and when an opt-in profile is absent, invalid or expired. In an *explicitly authorized* run, a bounded candidate set may include selected models/providers and, if intentionally enabled, other harnesses. Route selection must resolve to concrete configured identities before use.

Authorization identifies at minimum:
- eligible route/model (and permitted harness when applicable) identities and scope;
- allowed credential source/account/plan and its billing semantics;
- hard spend/overage limits and prohibited billing or training-consent transitions;
- task and permission scope, including allowed write or irreversible operations;
- validity and revocation/expiration semantics.

A pricing estimate or local token meter is not a hard billing stop; use actual provider/account spend limits wherever required. Native subscription sessions, bundled-plan endpoints and metered API routes are not interchangeable by default. Do not copy authenticated session material between runtimes or expose a union of unrelated secrets to all workers. Where credential isolation cannot be implemented, that candidate is unavailable, rather than silently relaxing the boundary.

This opt-in exception refines ADR-0014's **no implicit fallback** rule only for runs whose authorized candidate set and safeguards are proven. The existing implementation must continue to reject switching until the opt-in implementation and its required safety checks are actually ready. Documentation acceptance is not operational enablement.

### 3. Prefer continuity with minimal migration, not model churn

For a still-live worker, keep its harness, tools and session whenever safe. Classify the actual failure first:
- bounded, retryable throttling: honor observed retry/reset information, without unbounded loops;
- exhausted quota, account restriction or provider outage: avoid affected quota scope and consider an authorized alternative;
- authentication failure, unknown capacity/price, unknown side effects: do not silently change accounts, billing or execute a new mutable attempt;
- all permitted routes unavailable: persist a resumable waiting/blocked state and the next supported recheck.

The selection target is **verified completion at acceptable total cost and operator effort**, not the cheapest nominal token or a fixed cross-harness benchmark ranking. Use published benchmarks to inform candidates; don't overrule required capabilities or exact task evidence. Retain the selected route while usable to avoid gratuitous cache/context migration.

### 4. Harness transfer is a task handoff, not a session clone

A different harness may have incompatible tool surface, internal context, model auth, child-agent execution and session serialization. Do not promise lossless conversion of private or in-flight runtime state. At a safe handoff boundary, create/reconcile a *new execution attempt* from canonical Issue/Spec/ADR, remote Git/PR state, checkpoint, verified local diff, completed external side effects, exact SHA and permissions. Obtain current mutation ownership atomically (fencing); reject stale or concurrently alive mutators. If the old attempt's effects cannot be determined, require reconciliation before replay.

The lower-cost same-harness provider change and the higher-cost cross-harness attempt change are distinct operations. Support native resume as an optimization, not the only recovery path. Implementation belongs to [#100](https://github.com/rebuildup/dotfiles/issues/100)/[#101](https://github.com/rebuildup/dotfiles/issues/101) and related issue contracts, not to a second orchestration SoT.

### 5. Completion and human judgment are distinct gates

Agent output, a Herdr pane status, a green CI label or a successful model answer is not proof of task completion. Evaluate according to project-local quality profile and current SHA. For UI/native changes, use the project-init quality-gate's visual/native evidence handoff: explicit design/spec reference, actual target build/platform/viewport/state, observed discrepancies and unresolved human decisions.

Automate mechanical verification and independent review where appropriate; escalate only product value decisions, unsafe side effects, material design direction changes or explicit release authority. Do not interpret ticket-readiness approval as release authorization. `release-* -> main` remains explicitly authorized by the user; qualifying ticket PRs may continue to land autonomously under the existing policy.

- **[#92](https://github.com/rebuildup/dotfiles/issues/92)/[#94](https://github.com/rebuildup/dotfiles/issues/94)** provide classified failure and candidate assessment; facts without verified provenance stay unknown, not available.
- **[#100](https://github.com/rebuildup/dotfiles/issues/100)/[#101](https://github.com/rebuildup/dotfiles/issues/101)** own Herdr dispatch, cross-harness or cross-host handoff, safe recovery and distinct mutating attempts. A new router is not built in parallel.
- **[#102](https://github.com/rebuildup/dotfiles/issues/102)/[#103](https://github.com/rebuildup/dotfiles/issues/103)** own SHA-pinned gates, review and authorized ticket landing; **[#104](https://github.com/rebuildup/dotfiles/issues/104)/[#105](https://github.com/rebuildup/dotfiles/issues/105)** own negative/chaos and multi-OS real acceptance.
- **[#127](https://github.com/rebuildup/dotfiles/issues/127)** tracks outstanding integrations and safety gaps; no component's documented behavior counts as working until its independent tests and actual applicable environment acceptance exist.
- UI/operator tooling such as T3 Code is a separate **bounded fit-gap trial** ([#137](https://github.com/rebuildup/dotfiles/issues/137)) and not an automatic dependency of continuity.

## Rejected alternatives and trade-offs

- **Remove OMP/launcher guards and enable ambient fallback:** could misroute credentials, ignore native billing limits or widen tool permissions.
- **Switch harness whenever a model is slow:** increases state migration, loses caches and may duplicate mutations without establishing that the old attempt failed.
- **Create a universal harness/gateway/UI immediately:** duplicates Herdr, the existing launcher, native harness capabilities and project-init before proving a missing guarantee.
- **Require full tracing or historical measurement before acting:** would delay an already identified failure. Evaluate new mechanisms through targeted positive/negative tests and ordinary work evidence instead.
- **Guarantee every product/design choice automatically:** confuses deterministic checks with human product judgment and risks silent design drift.

This decision commits to bounded continuity and current authority boundaries. Exact CLI/schema/credential broker design, target-provider support and rollout on each OS are implementation questions in the referenced Issues, not facts asserted by this ADR.
